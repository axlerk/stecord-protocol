directory is self-contained; `cavlc_tables.py` is generated from the app's own CAVLC tables. The paths and commit hashes below, and
the `tools/` and `docs/` paths in the comments of the Python files, name files of that private tree; they are kept as a record of
origin and do not resolve here. A fix in the research code has to be copied here by hand, and the test vectors re-checked.

## What the parser claims

The parser follows ITU-T H.264 clauses 7.3.2-7.3.5 and 9.2 "read from memory of the standard and cross-validated against ffmpeg 8.1.1
decodes of the clips" (the header of `h264x.py`; ffmpeg was a test oracle that decoded the same clips, no ffmpeg code is in the
parser). It was validated by exact stop bits on 28 phone-written clips, 112 stego files and the x264 sweeps (2026-11-08), and in
Swift against Python (2026-11-09). It is **not** validated against the standard's conformance streams.

## The CAVLC tables

`cavlc_tables.py` holds the code tables of ITU-T Rec. H.264 clause 9.2: `coeff_token` (Table 9-5), `total_zeros` (Tables 9-7,
9-8 and 9-9 (a)), `run_before` (Table 9-10) and the `coded_block_pattern` mapping of Table 9-4. They are data fixed by the
standard; every conforming H.264 decoder uses the same values.

**Where the values come from.** `gen_tables_from_swift.py` reads the numeric arrays of the app's
`StecordCore/Engine/CavlcTables.swift`, keys every code word by the standard's syntax-element values (`(TrailingOnes, TotalCoeff)`,
`tzVlcIndex` and `total_zeros`, `zerosLeft` and `run_before`, `codeNum`), writes the code words as bit strings, checks that every
code is prefix-free with a Kraft sum of at most 1 and that the shapes are the standard's, and writes `cavlc_tables.py`. The Swift
file is written by the app's `scripts/gen_cavlc_tables.py`, which carries the tables as transcribed from the standard's tables,
builds the 6-bit fixed-length `coeff_token` column (8 <= nC) from the standard's rule, and runs the same checks (the app's record:
its decision D12 and the message of commit f1458dd). Regenerate in the app's source tree with `python3 -I gen_tables_from_swift.py`;
`--check` compares instead of writing.

**History.** Until 2026-11-16 this directory held a different `cavlc_tables.py`, whose values had been machine-extracted from the
array initialisers of FFmpeg's `libavcodec/h264_cavlc.c` and `h264data.c` (FFmpeg is licensed under LGPL-2.1-or-later, **recalled**).
It was replaced by the generated file above; no text, name or layout of the old file is kept. Before the replacement, both modules
were loaded and compared entry by entry (2026-11-16): 32 tables, 544 entries (448 code words in 30 variable-length codes and 2 x 48
`coded_block_pattern` values), all equal; the zero-length padding of the old chroma-DC `total_zeros` rows marked "no code word"
and has no counterpart in the new layout. The lookup tables that `h264x.py` builds from the new file are identical, cell by cell
(284 440 cells), to those the original `h264x.py` builds from the old one, and the test vectors and the test suite pass unchanged.

**Tests.** `tests/test_stecord.py` checks that every code of `cavlc_tables.py` is prefix-free with a Kraft sum of at most 1 and
has the standard's shape (`test_cavlc_tables_are_prefix_codes`), and that `cavlc_tables.py` is exactly what the generator writes
from the Swift file (`test_cavlc_tables_match_the_swift_tables`, skipped where the Swift file is absent, as in the public mirror).
The parse succeeding with exact stop bits on 28 phone clips remains the stronger evidence that the code words are right.
